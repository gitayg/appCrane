# FIPS 140-3 mode

AppCrane can run with every cryptographic operation it performs itself going
through an OpenSSL FIPS provider. AppCrane does not contain a cryptographic
module of its own: FIPS 140-3 validation belongs to the OpenSSL FIPS provider
that Node is linked against, and to the modules inside Caddy, the database
images and the host OS. This page lists what AppCrane does, what the deployer
must provide, and how to check it.

## What AppCrane does

| Area | Algorithm | Notes |
|---|---|---|
| Secrets at rest (env vars, tokens, keys in SQLite) | AES-256-GCM, 16-byte tag, random IV | `server/services/encryption.js` |
| Backups | AES-256-GCM | `server/services/backupCrypto.js` |
| API keys, session tokens, webhook and tenant signatures | SHA-256, HMAC-SHA256, `crypto.randomBytes` | |
| User passwords | PBKDF2-HMAC-SHA256, 600,000 iterations, 16-byte salt, 32-byte output | Stored as `pbkdf2-sha256$<iterations>$<salt>$<hash>` (base64). 600,000 is the OWASP Password Storage Cheat Sheet figure for PBKDF2-HMAC-SHA256. Measured on an Apple M5 Max (Node 22.22.0, OpenSSL 3.6.4): about 96-140 ms per hash. |
| Legacy passwords | scrypt | Written before this change. They still verify, and are re-hashed to PBKDF2 at that user's next password sign-in. |
| Off-site backup (S3) | SigV4 (HMAC-SHA256), payload SHA-256 | DeleteObjects sends `x-amz-checksum-sha256` plus `x-amz-sdk-checksum-algorithm: SHA256` instead of `Content-MD5` |
| MariaDB data-at-rest key file | AES-256-CBC, key derived with EVP_BytesToKey/SHA-1 (default) or PBKDF2-HMAC-SHA256 (`APPCRANE_TDE_KDF=pbkdf2-sha256`) | See below |
| Database certificates (`dbPki.js`) | EC P-256, ECDSA-SHA256 | The subject/authority key identifier is SHA-1 of the public key (RFC 5280 4.2.1.2 method 1). That is an identifier, not a security function, and SHA-1 hashing is still in the OpenSSL FIPS provider. Documented exception; not changed. |
| TOTP (MFA) | HMAC-SHA1 by default (RFC 6238) | HMAC-SHA1 is still an approved HMAC. |
| Outbound TLS (SIEM) | TLS 1.2 minimum | With a FIPS provider, OpenSSL offers only approved cipher suites. |

`Math.random` appears only for timing jitter and a scratch directory suffix,
never for a secret.

### APPCRANE_FIPS

| Value | Effect |
|---|---|
| `off` (default) | Nothing is checked. |
| `prefer` | AppCrane starts either way and logs a warning when the FIPS provider is not active or the self-check fails. |
| `require` | AppCrane refuses to start unless `crypto.getFips()` returns 1 and the self-check passes. |

The self-check (`server/services/fipsMode.js`) runs known-answer tests for
SHA-256 (FIPS 180-2 "abc"), HMAC-SHA256 (RFC 4231 case 2), PBKDF2-HMAC-SHA256
(RFC 7914 section 11) and AES-256-GCM (GCM spec test case 14, plus a rejected
tampered tag), draws 32 random bytes, and checks that MD5 is refused. If MD5
still works, the FIPS provider is not the one answering, and `require` refuses
to start.

Settings -> Cryptography shows the mode, whether the FIPS provider is active,
the OpenSSL version, the self-check, and what is still on a non-approved
algorithm: users with scrypt passwords, and a MariaDB key file wrapped with
SHA-1.

### Passwords under a FIPS provider

The OpenSSL FIPS provider does not include scrypt. Under it, a user whose
password is still scrypt cannot sign in with it (the verify fails closed), and
an admin has to reset that password. The Cryptography card shows how many users
are affected. To avoid this, run in `prefer` mode, or without FIPS, until that
count is 0, because each user's next sign-in converts their hash.

### The MariaDB key file

The SHA-1 here is not a database password. It wraps the key file that MariaDB's
`file_key_management` plugin reads, in the format of `openssl enc -aes-256-cbc`.
MariaDB before 12.0 accepts only the EVP_BytesToKey/SHA-1 derivation. MariaDB
12.0 added `file_key_management_digest` and `file_key_management_use_pbkdf2`.

To move to PBKDF2-HMAC-SHA256:

1. Set `MANAGED_DB_MARIADB_IMAGE` to a MariaDB 12.x image (AppCrane refuses
   `APPCRANE_TDE_KDF=pbkdf2-sha256` with an older image tag before it touches
   the container).
2. Set `APPCRANE_TDE_KDF=pbkdf2-sha256` and restart AppCrane.
3. At the next ensure, the managed MariaDB container is recreated once. The key
   file is rewritten with PBKDF2-HMAC-SHA256 (600,000 iterations), and the
   server starts with `--file-key-management-digest=sha256
   --file-key-management-use-pbkdf2=600000`.

The 256-bit data key inside the file does not change, so no tablespace is
re-encrypted and no password or `ALTER USER` is involved. Unsetting the variable
switches back the same way. A server that has never had encryption on is not
affected.

## What the deployer must provide

1. **Node linked to a CMVP-validated OpenSSL FIPS provider**, with the provider
   installed and `fipsmodule.cnf` generated by `openssl fipsinstall`, and Node
   started with `--enable-fips` or `--force-fips` (or with the provider
   activated in the OpenSSL config that Node loads). A stock Node build does not
   have this: `crypto.getFips()` returns 0.
2. **Caddy built with a validated Go cryptographic module** (Go 1.24+ built
   with `GOFIPS140`, or a vendor FIPS build; check the module's CMVP status
   before relying on it). Caddy terminates TLS for every app, and Node's
   provider does not cover it.
3. **FIPS base images** for the managed databases (Postgres, MariaDB, Mongo,
   Redis) and the coder image, with their OpenSSL in FIPS mode. For MariaDB,
   use a 12.x image if you want the PBKDF2 key-file derivation.
4. **Host OS in FIPS mode** (for example `fips-mode-setup --enable` on RHEL, or
   Ubuntu Pro FIPS), so the kernel, SSH and Docker use validated modules too.
5. **Nothing for S3, usually.** AWS's DeleteObjects page still says, for general
   purpose buckets, that "The Content-MD5 request header is required for all
   Multi-Object Delete requests", while its directory-bucket text and request
   syntax accept `x-amz-checksum-sha256` instead. If a server answers 400 asking
   for Content-MD5, AppCrane retries with it when MD5 is available. Under FIPS,
   MD5 is not available, so AppCrane falls back to one DeleteObject call per key
   (slower retention pruning, same result).

## How to verify

```bash
node -p "require('crypto').getFips()"                         # 1
node -e "require('crypto').createHash('md5')"                 # must throw
APPCRANE_FIPS=require node server/index.js                    # starts; refuses otherwise
```

Then open Settings -> Cryptography. It should show: provider active, self-check
passed, MD5 refused, and nothing under "Still on a non-approved algorithm".
Check Caddy, the images and the host with their own tools: AppCrane cannot see
them.

## The claim

Only when all of the above are true for a deployment:

> This deployment of AppCrane operates in FIPS 140-3 mode using validated
> cryptographic modules.

Name the module and its CMVP certificate number. Do not make the claim for
AppCrane as a product, for a deployment where only Node is in FIPS mode, or for
a deployment where the Cryptography card lists anything still on a legacy
algorithm. AppCrane itself is not "FIPS validated" or "FIPS certified".
